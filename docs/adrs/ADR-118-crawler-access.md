# ADR-118-crawler-access: `robots.txt` allows everything, names the sitemap, and allows twenty AI crawlers by name; nothing is disallowed

- Status: ACCEPTED (frozen) -- 2026-09-21
- Issue: #118 -- Architecture: freeze the JSON-only Tree format (`elsa-tree/4`)
- Spec: `docs/specs/application.md` 16.1
- Amends: `docs/adrs/ADR-5-url-scheme.md` (`/robots.txt` joins the grammar of
  4.1), `ADR-5-repository-layout.md` (`src/findability/robots.ts` and
  `src/app/[lang]/robots.txt/route.ts`) and `ADR-5-testing-approach.md`
  (`tests/findability/robots.test.ts`, and `robots.txt` in `findability.spec.ts`
  and in `deployment.spec.ts`'s sweep). Also `ADR-11-public-base-url.md`: the
  `Sitemap:` line is an absolute URL built from `ELSA_BASE_URL`, so the variable
  has a consumer that is not the canonical link, and the request origin answers
  when it is unset

## Context

There is no `robots.txt` today, which means "allowed" to every crawler that follows the
standard -- an absent file is a permission, not a refusal. So the file is not needed to
be crawled. It is needed for two other things:

- **It is where the sitemap is announced.** `Sitemap:` in `robots.txt` is the one
  discovery mechanism every search engine reads without being told a URL
  (`ADR-118-sitemap-and-alternates.md`).
- **It is where the owner's intent is written down.** The owner asked, on 2026-09-21, for
  the Trees to be findable by "the crawlers that feed AI assistants", and named eight
  agents: `GPTBot`, `ClaudeBot`, `Claude-Web`, `PerplexityBot`, `Google-Extended`,
  `Bingbot`, `Applebot` and `CCBot`. **Exactly one of the eight is not a crawler at
  all**: `Google-Extended` is a control token with no fetcher behind it, read only to
  decide whether content already collected by Googlebot may be used for AI training. The
  table of decision 3 names the other operators' control tokens beside it --
  `Applebot-Extended` among them -- for the same reason, which is why twenty tokens
  answer a list of eight. A site that says nothing is, for most of these tokens, allowed
  by default -- but the default is the operator's to change, and a file that names each
  one is a statement that survives a change of default and that a reader can check.

## Decision

1. **`GET /robots.txt`, generated by the server**, not a static file: it names the
   sitemap's absolute URL, which depends on the deployment (`ELSA_BASE_URL`, or the
   request's origin when the variable is unset -- `application.md` 16).
2. **A `User-agent: *` block with `Allow: /`**, and no `Disallow` line anywhere in the
   file.
3. **One `Allow: /` block per named agent**, for twenty tokens, grouped by operator:
   OpenAI, Anthropic, Perplexity, Google, Microsoft, Apple, Meta, Common Crawl, Amazon,
   ByteDance and DuckDuckGo -- each operator's crawler, its search or answer index, and,
   where the operator has one, its AI-training control token and its user-initiated
   fetcher. **The tokens themselves are listed once, in `application.md` 16.1**, as their
   operators published them on 2026-09-21. This ADR deliberately does not repeat them:
   see point 6 -- a copy here would be the second table the list must not have.

4. **Nothing is disallowed, the image route included.** The issue offered to exclude "the
   image route's enlarged views if you judge them noise". They are not a URL: the
   enlarged view is the Sheet a click opens over the page, and the only address behind it
   is the picture's own file, `/images/<file>` (`application.md` 12.3). Disallowing that
   path would hide the Tree's pictures from image search and would remove the one thing a
   crawler needs to render a result with a picture, in exchange for nothing.
5. **The named blocks are declaratory and the wildcard is what does the work.** An agent
   whose token is misspelt here, or renamed by its operator tomorrow, matches
   `User-agent: *` and is allowed. That is the safety property of this decision: the list
   can go stale without ever becoming a refusal.
6. **The list is data, not architecture.** Adding or removing a token changes one table in
   16.1 and one array in the generator. It does not need an `architecture` issue, because
   nothing depends on which tokens are in it -- which is the same sentence as 5, said to
   the next person who wants to change it.

## Alternatives rejected

- **No `robots.txt` at all.** Already the permissive state, and it loses the `Sitemap:`
  line, which is the reason the file is worth generating.
- **A static `public/robots.txt`.** The sitemap's URL is absolute and deployment-specific;
  a static file would either hard-code one host or omit the line that matters.
- **`User-agent: *` with `Allow: /` and no named blocks.** Enough for a crawler that
  merges the wildcard with its own rules, and not for the several that read only their
  own block. It also leaves the owner's intent nowhere in the repository.
- **Disallowing `/images/`.** See decision 4.
- **Disallowing the walk's deep URLs** -- the paths that carry a Trail,
  `/<tree>/a/b/c` -- as near-duplicates of the Node's own page. They are already handled
  correctly and by the better mechanism: every page carries `<link rel="canonical">` to
  the Node's empty-Trail URL (4.1), and only that URL is in the sitemap. A `Disallow`
  would stop a crawler reading the page and so stop it reading the canonical link, which
  is the opposite of what it is for.
- **Naming the AI crawlers in a `Disallow`** -- the choice many sites made. Not the
  owner's direction: the Trees are public research output under CC BY 4.0 and being read
  by an assistant is the point.

## Consequences

- The file says the same thing three ways (the wildcard, the named blocks, and the absence
  of any `Disallow`), which is deliberate: it cannot be made stricter by a typo.
- `ELSA_BASE_URL` becomes load-bearing for a public deployment in a way it was not: the
  canonical link degrades gracefully to a path without it (ADR-11), but `Sitemap:` and
  the sitemap's own `<loc>` elements must be absolute. `docs/deployment.md` says so next
  to the variable (issue #120).
- A test asserts that every token in 16.1's table appears in the generated file and that
  the file contains no `Disallow` line; a token added to the table without being added to
  the generator fails it (issue #120).
