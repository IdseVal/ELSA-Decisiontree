# ADR-118-llms-txt: `/llms.txt` is generated from the manifest and points at the dataset; there is no `llms-full.txt`

- Status: ACCEPTED (frozen) -- 2026-09-21
- Issue: #118 -- Architecture: freeze the JSON-only Tree format (`elsa-tree/4`)
- Spec: `docs/specs/application.md` 16.5
- Amends: `docs/adrs/ADR-5-url-scheme.md` (`/llms.txt` joins the grammar of 4.1),
  `ADR-5-repository-layout.md` (`src/findability/llms.ts` and
  `src/app/[lang]/llms.txt/route.ts`) and `ADR-5-testing-approach.md`
  (`tests/findability/llms.test.ts`, and `llms.txt` in `findability.spec.ts` and
  in `deployment.spec.ts`'s sweep). Also `ADR-11-public-base-url.md`: every URL
  the document lists is absolute and built from the base

## Context

`llms.txt` is a convention -- a Markdown file at the root of a site that tells an agent,
in one short fetch, what the site is and where the material it wants actually lives. The
v2 proposal requires exactly one thing, an H1 with the site's name, and allows, in order:
a blockquote summary, free-form Markdown without headings, and H2 sections whose bodies
are lists of `- [name](url): note`. The convention also describes an `llms-full.txt`
holding all of a site's documentation in one file.

This site is an unusual fit and a good one. An agent that lands on a Node page sees one
question and two buttons; it has no way to know that behind the walk there is a complete,
validated, licensed dataset at one URL. That is the single sentence `llms.txt` exists to
say.

## Decision

1. **`GET /llms.txt`**, generated from the served Tree's manifest at request time, served
   as `text/plain; charset=utf-8` with `Cache-Control: public, max-age=3600` and no
   cookie. Markdown content, plain-text media type: that is what the convention's readers
   expect, and `text/markdown` is not reliably handled by the middle of the internet.
2. **Its shape is the list in `application.md` 16.5**, in the order the convention
   gives: an H1, a blockquote, a free-form paragraph that is chrome and not Tree
   content, and the sections `## The dataset`, `## Walking the Tree`, `## Languages`
   and `## Licence`. **What goes in each is written out there, once, and this ADR does
   not repeat it**, for the reason `ADR-118-crawler-access.md` gives for the token
   list. The two choices inside that shape are decided here: the blockquote is the
   Tree's description **in the default language**, falling back to the root Node's when
   the manifest has none, so the file is never headless; and `## Walking the Tree`
   states the URL grammar of `application.md` 4.1 rather than listing addresses, so an
   agent can reach any step without guessing and the file does not grow with the Tree.
3. **Every URL in it is absolute**, built from the same base as the sitemap
   (`ELSA_BASE_URL`, else the request's origin), because the file is read away from the
   site that served it.
4. **There is no `llms-full.txt`.** The complete content of this site in one document
   already exists, is validated against a published schema, and is served at
   `/<tree-id>/tree.json`. `llms.txt` names it in its first section.
5. **`llms.txt` contains no Tree content beyond the manifest's title and description.**
   It is a signpost. Node titles, descriptions and Sources are in the pages, in the
   sitemap and in the dataset; a fourth copy would be the one that goes stale.

## Alternatives rejected

- **Also serving `llms-full.txt` as Markdown of every Node.** The convention describes it
  and it would be a day's work. Rejected: it is a second complete serialisation of the
  same content, generated by a second renderer, with no schema and no validator -- the
  exact shape `ADR-118-json-serialisation.md` rejected inside the repository, at the edge
  of the system instead. An agent that wants everything is one fetch from `tree.json`,
  and `tree.json` is the copy that cannot drift because it is the source.
- **A static `llms.txt` in the repository.** Its URLs are absolute and
  deployment-specific, and its first two lines are the Tree's title and description,
  which are Tree data. A static file would hard-code one host and one Tree.
- **Serving it as `text/markdown`.** Correct on paper; in practice a share of proxies and
  clients treat an unfamiliar media type as a download. The content is Markdown either
  way.
- **Listing every Node as a link in an H2 section**, which is what most `llms.txt` files
  do for a documentation site. For a Tree of a thousand Nodes that is a file nobody
  reads, and the sitemap is the machine-readable list of exactly those URLs, already
  generated and already correct.
- **Nothing at all**, on the argument that `llms.txt` is a convention no operator has
  committed to. It costs one generated route, and the alternative for an agent that lands
  on a leaf of the walk is to guess that a dataset exists.

## Consequences

- `llms.txt` and the sitemap share the base-URL rule and the plain-text reduction; they
  are two renderings of facts the loader already holds, and neither carries a fact of its
  own.
- The route joins the no-cookie and own-origin sweeps with the rest of section 15 and 16
  (issue #121).
- If the owner later wants a Markdown rendering of the whole walk, it is a new issue with
  its own decision, and this ADR is the record of why it was not done by default.
